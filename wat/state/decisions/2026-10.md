### 2026-10-21: A secondary capture port is not the profile's gameplay transport

**Agent:** RustDev
**Status:** Accepted (`dfa1413`)
**Rationale:** `tcp_ports()` drives the portable pcap filter, which is single-transport; declaring ARC Raiders' TCP 443 there replaced its UDP 7600-7777 filter, and the existing guard test caught it. The WinDivert both-transports path needs a second clause, not a different primary transport.
**Impact:** `GameConfig::capture_tcp_ports()` is the new opt-in and defaults to `(0, 0)`. ARC Raiders sets it to `(443, 443)`; `tcp_ports()` stays `(0, 0)`, and process-targeted capture stays UDP-only until per-flow TCP attribution exists.

### 2026-10-21: Zero return bytes through a forwarding relay means a transport split, not a relay fault

**Agent:** RustDev + QAEngineer
**Status:** Accepted (`wat/state/current-phase.md`, `59f20c8`; follow-on work open)
**Rationale:** the Frankfurt relay's egress equaled the client-to-server bytes and
`drops_relay_send_errors` stayed zero, so the relay forwarded the game's UDP. The live game also
held TCP `34.160.204.112:443`, which the UDP-only interceptor never captured, so the server saw one
session from two source addresses. A profile-only `tcp_ports` entry was rejected because it makes
the capture filter TCP-only and drops the game's UDP.
**Impact:** the relay is exonerated for the ARC Raiders join failure; the fix is a both-transports
interceptor that carries UDP and the game's TCP in one session. Until that lands, ARC Raiders can
only use a relay for its UDP half.

### 2026-10-21: The relay is ranked by the leg it owns, not by the leg the client can see

**Agent:** RustDev + QAEngineer
**Status:** Accepted (`client/src/route/relay_choice.rs`, `59f20c8`)
**Rationale:** the client-leg race answers "which relay is closest to me", but for a game server in
another region the server-side leg decides whether the relay is usable at all. A relay on the wrong
side of the world can be rejected by the server's region check, and its relay-to-server latency
cannot be recovered by a shorter client hop. Field evidence: a European server was being carried
through Singapore while the European relay existed.
**Impact:** `sort_scored` compares `dest_leg_us` in 50 ms buckets first, then total path plus twice
the jitter, then the address for a stable tie-break. The new test pins a Brussels server choosing
the Frankfurt relay over a relay with a much shorter client leg.

### 2026-10-18: A hold is released by the engine, not by whatever frame the GUI manages

**Agent:** RustDev + QAEngineer
**Status:** Accepted (`client/src/engine.rs`, `client/src/interceptor/traits.rs`, `client-gui/src/app.rs`)
**Rationale:** the hold shipped in `5749664` had exactly one caller that could
end it: the GUI's per-frame `release_tunnelling`. A frame loop stopped (or
starved) while a player is actually in a match is the normal case, so the one
moment the hold needed to end was the one moment its release could wait. The
timing was also wrong at the other end: the zero-click path connects a relay
while the hold is still waiting for a server, and the hold's only other exit was
the two-minute fallback, which would put a wrong relay in front of a player whose
wait was over because the game had left.
**Impact:** `InterceptorHandle` exposes the tunnelling switch it already owned
(`tunnelling_switch()`), and `LightSpeedEngine::release_hold_when_connected` arms
a task on the engine's own multi-threaded runtime that waits for the predicate and
flips the switch, at most 100 ms after the relay connects. The destination-aware
release still comes first on every run that finds its server and aborts the
watcher; `release_tunnelling` also aborts it, so a stale watcher can never release
a later run's hold. A backend with no gate returns `false` from the arming call,
matching `hold_tunnelling`, so "nothing is being held" stays distinguishable from
"held, release pending".
**Alternatives Considered:** driving `ctx.request_repaint()` from a timer was
rejected because it makes the frame loop a promise the GUI never had to keep and
couples the hold's correctness to viewport behaviour. Polling the relay from the
engine only when a server is missing was rejected as a second source of truth for
"connected" when the status write already happens on the runtime.
**Verification:** `cargo fmt --all --check` clean; `cargo clippy -p
lightspeed-gui -p lightspeed-client --all-targets -- -D warnings` clean;
`cargo test -p lightspeed-client --lib` 552 passed; `cargo test -p
lightspeed-client --features windivert-redirect --lib interceptor::windows` 11
passed; `cargo test -p lightspeed-gui --bin lightspeed-gui` 127 passed. The new
`release_hold_when_connected_is_armed_only_for_a_gated_run` pins that an engine
with no interceptor and a backend with no gate both report `false` rather than
promising a release. **NOT verified:** the watcher firing against a live game is
not reproduced by any test here: the mock interceptor has no gate, and the
WinDivert gate needs a live run. The claim it fixes (a hold outliving its relay)
is untested in the field; the next live session should show the new trace line
within a second of `Following the game server` or of the fallback.

### 2026-10-18: The relay verdict is measured on movement, and a switch is only safe while held

**Agent:** RustDev + QAEngineer
**Status:** Accepted (`client/src/interceptor/traits.rs`, `client/src/interceptor/windows.rs`,
`client/src/engine.rs`, `client-gui/src/app.rs`)
**Rationale:** the counters said a flow was *decided* to relay, never whether the
datagram left the machine. A relay that is not taking this session, or a send that
fails, therefore read exactly like a healthy match - the worst failure this app
can produce, because the player experiences it as packet loss and has no way to
learn it is the relay. The verdict compares a new `packets_tunnel_sent` against
`packets_intercepted` per window, after a ten-second settle, so one lost UDP
datagram is not a fault and a fifth of a second's traffic never leaving is.
**Impact:** `InterceptorCounters::packets_tunnel_sent` counts only sends that
returned Ok, the snapshot carries it, and the GUI logs one sentence when the
verdict changes (`Relay verdict: ...`). Separately, `switch_is_safe` pins the
rule that a relay change may only be applied while tunnelling is withheld (or on
a backend with no gate), because the tunnel reads the current relay on every
packet and a switch during a live match would send datagrams to a relay that has
not registered this session yet.
**Alternatives Considered:** counting sends at `send_datagram` inside the tunnel
module was rejected because that helper is shared with the CLI's multipath path
and would double-count there; a cumulative ratio over the whole run was rejected
because a healthy first minute would mask a broken one forever.
**Verification:** `cargo fmt --all --check`; `cargo clippy -p lightspeed-gui -p
lightspeed-client --all-targets -- -D warnings` and the same with
`--features windivert-redirect`; `lightspeed-gui` 130 passed, `lightspeed-client`
(with the feature) 557 passed. New tests: `relay_health_reads_movement_not_totals`,
`relay_health_tolerates_loss_and_a_still_flow`,
`a_gate_off_is_the_only_safe_moment_for_a_relay_switch`. **NOT verified:** no
live run has yet produced an `Unsent` verdict; the healthy path is what the live
runs so far would exercise, and a real relay-side failure is not something the
suite can create.

### 2026-10-17: Relay spread is second-slowest minus fastest, over five probes

**Agent:** RustDev + QAEngineer
**Status:** Accepted
**Rationale:** The whole-path ranking doubles jitter (`JITTER_WEIGHT = 2`) but was always handed zero, because each relay was probed once. Measuring spread over a handful of whole-millisecond probes makes the estimator matter more than the sample count: `max - min` lets one spike decide; nearest-rank p90 - p10 at n=5 is exactly `max - min` (`ceil(0.9n)` is the last sample and p10 is the first); linear-interpolated p90 - p10 still read 115 ms against a 3 ms truth for one spike. The owner's goal is the lowest latency and the most stable connection, and on his congested mobile link the slow probe is the realistic outlier while a fast one is just a quiet moment. Holding out exactly one probe at each end (second-slowest minus fastest) reports that spike as 3 ms, and five probes leave three middle samples.
**Impact:** `client-gui/src/discovery.rs` gains `RelaySample` (median + spread), `RELAY_PROBES = 5` and `measure_spreads_blocking`; the GUI's client-leg measurement uses it, so `client_jitter_us` is a measured value in relay choice for the first time. Five tests pin the estimator (steady link, one spike, one probe, empty, and the blocking measurement's ordering with an unanswered relay). The chooser's scoring is unchanged.
**Alternatives Considered:** Three probes (the half-finished change's number): collapses to `max - min` once one is held out at each end. Nearest-rank p90 - p10: no tail-off at these sample counts. Linear-interpolated p90 - p10: passes simple tests, but a single spike still contributes 75% of its excess. More probes: real cost per relay on every recheck, for a signal that already separates a steady relay from a spiky one.

### 2026-10-07: WF-055 plan reworked by adversarial review - one resolution API, no leaks, five owner gates

**Agent:** Architect + RustDev (review round, following the research round above)
**Status:** Accepted for the plan (built-ins unchanged); owner gates pending
**Rationale:** the same plan was put through a second, adversarial pass, and five of its calls did not survive.
Each rejection is recorded with the reason, so none of them gets re-proposed as an improvement.

- **`resolve()` is the only public resolution API.** Precedence is fixed: built-in `detect_game` first, then a
  user profile by exact key, then the existing Unknown game error shape extended with a `Your profiles:` line
  listing the user keys. `detect_game` becomes private (`pub(crate)`). Built-in first means a shipped key can
  never change meaning under a user's feet, and it keeps the registry guards and the docs/website counts
  meaning "built-in games" exactly as before.
- **The trait method becomes `fn process_names(&self) -> Vec<&str>`.** A profile that owns its `String`s now
  borrows from `&self`, which is what makes an owning profile possible at all. The 23 built-in impls are
  mechanical edits.
- **`Box::leak` is rejected.** The first draft recommended interning each user profile's strings at load,
  citing `process_name_table`. That precedent leaks once, for `'static` built-in names. A user profile leaks on
  every load, and the GUI calls `reload()` after each editor save, so the leak **compounds on every save** for
  the life of the session. The 64-profile cap bounds one file, not a session of edits, so it bounds nothing
  here. A GUI the user is meant to edit freely cannot pay that.
- **A blanket default that calls `process_names()` is declared invalid.** It was the tempting way to skip the 23
  impl edits, but it's circular: the method it would delegate to is the one whose signature has to change, so
  the default either keeps `&[&str]` (a `String`-owning profile still can't implement it) or widens the trait
  anyway. The mechanical edits are the honest path.
- **`InterceptorConfig` carries resolved flags.** `dynamic_server`, `transport` and `process_names` arrive
  resolved by `resolve()`, replacing the display-name lookups (`dynamic_server_for_name`,
  `process_names_for_name`) that could quietly miss for a custom profile. The test that names the case: **a
  `dynamic_server = true` custom profile must not seed from `initial_routes.first()`**, or a rotating title
  tunnels at a lobby address the match abandoned.
- **Picker scope is pending owner gate OQ5.** The default is a minimal Windows scanner extension: running
  processes, image path, start-time identity, with the snapshot published off the UI thread and **nothing
  polled on the egui thread**. The shell-based scanner already runs synchronously on the UI thread today,
  which is part of why it misbehaves; a pick list that pauses the UI on `tasklist` is not shippable. Native
  Win32 enumeration, launcher/child trees and the non-Windows variants stay behind OQ5.
- **macOS parity claim withdrawn.** The plan no longer implies macOS process mode reaches parity. pf can't
  match a PID, and attributing another process's sockets needs Apple's `com.apple.system-task-ports`
  entitlement, which a paid account gates and `[COST_STUB]` rules out. Section 5.4 now ships the honest bound
  only if the owner accepts it under OQ4.
- **Built-ins stay untouched.** Data-driven built-ins (loading the shipped 23 through the same profile store)
  were rejected again in 5.3: they would put shipped games on the same footing as user entries, empty out the
  count guards and hand a user-editable file the power to regress a built-in port or process name.

**The five owner gates.** Section 8 is where they're answered; none of them is resolved by this entry.

1. Storage: per-user `profiles.toml` versus a `lightspeed.toml` section (recommended: per-user file).
2. Scope: any user-marked process versus games-only (recommended: any, behind the public-destination rule, the
   denylist and the flow cap).
3. macOS scope (OQ4): accept the documented best-effort ceiling and ship, or hold macOS at port-set parity
   (recommended: accept the bound, since the alternative is waiting on an entitlement we have no path to).
4. Discussion #146: post a progress reply pointing at P1 once it lands, or stay silent until then.
5. Process picker scope (OQ5): the minimal Windows scanner extension versus the larger cross-platform scanner
   (recommended: minimal, per above).

**Impact:** phase 1 of the plan (profiles, saved servers, `resolve()`, the widened trait, resolved flags, CLI
and GUI surfaces, wiring the currently inert custom port range into the target) was executed against these
corrections. Built-in behaviour is unchanged: same registry, same wire ids, same count guards, same filters.
No protocol change, so no wire-format risk and nothing for a relay to update.
**Alternatives Considered:** the rejected list above - `Box::leak` interning, a blanket `process_names()`
 default, display-name lookups in `InterceptorConfig`, `initial_routes.first()` seeding for rotating titles,
 data-driven built-ins, a macOS Network Extension, and picking the Windows attribution source (FLOW vs SOCKET)
 before the B-3 numbers land.
**Verification:** `rg -n "Box::leak" docs/design/custom-games-and-process-targeting.md` reports it only inside
 section 4.4 as rejected, and the precedence text for `resolve()` is present in 4.3. No application behaviour
 was exercised this round, so no tests were run; the plan's own gates (section 6.2 field gate, the B-1 and B-3
 benchmarks) still stand between this document and a ship claim.

### 2026-10-05: The GUI bundles real fallbacks, and a gate keeps them honest

**Agent:** RustDev + QAEngineer
**Status:** Accepted (`client-gui/src/app.rs`, `client-gui/assets/fonts/`)
**Rationale:** Measured, not assumed, and the measurement corrected the prior
review. The bundled Inter is a 230-codepoint subset with no Cyrillic, no Greek and
no CJK, so coverage rested entirely on the fallback chains: Japanese left 173 of
178 non-ASCII catalog characters undrawable, Korean 160 of 162, Simplified
Chinese 176 of 181. Russian was the surprise - 0 uncovered in regular text,
because epaint's built-in Ubuntu-Light carries 214 Cyrillic codepoints, but 52 of
54 uncovered in `semibold`, whose chain was `["inter_semibold", "inter"]` with no
fallback at all. Every emphasised label in a translated settings panel was tofu
while the body text beside it was fine.
**Impact:** three Noto CJK faces (JP/KR/SC, OFL) are subset with `pyftsubset` to
the glyphs the catalogs use plus a Latin/punctuation safety set - **0.23 MB
against the 5 MB budget**, because the full faces are 4.5-8.3 MB each.
`font_definitions()` builds real fallback chains for all three families, and the
CJK faces are ordered by the active locale: the subsets overlap (127 of the
Chinese catalog's 172 Han characters also exist in the Japanese face), so a fixed
order would draw Chinese text with Japanese glyphs. `main.rs` resolves the
language before the first frame and Settings re-installs on a change.
**Alternatives Considered:** loading the Windows CJK fonts at runtime was rejected
because they are optional features on a modern Windows install - the app would
render boxes on the machines least likely to have the language pack, which is the
exact population that needs them; shipping the unsubset faces was rejected on the
size budget; relying on epaint's built-in fonts was rejected because they carry
no CJK at all.
**Verification:** `every_catalog_glyph_is_drawable_in_every_family` asserts every
non-ASCII catalog character is drawable by every installed family, read from the
real `FontDefinitions` rather than a copy of the chains, and it was
**mutation-checked** - restoring the old Inter-only `semibold` chain fails it with
the characters and families named. Then verified by looking: the Japanese build
draws `リレー未選択` / `トレイに隠す` / `設定` / `自動（検出）`, the Russian settings
panel draws `Настройки` / `Язык` / `Конфиденциальность` in semibold Cyrillic, and
the machine was left as found (config written for the test, then removed).

### 2026-10-05: The wiki sync uses GITHUB_TOKEN - measured, after two probes lied

**Agent:** DevOps + QAEngineer
**Status:** Accepted (`scripts/sync-wiki.py`, `.github/workflows/wiki.yml`)
**Rationale:** `Sync Wiki` failed on every run from 2026-08-03, and the revision
before that swallowed the failure with `|| echo`, so the docs had never reached
the wiki - it held only its auto-generated Home page. The visible cause was a 403
on `lightspeed.wiki.git`, and the obvious diagnosis (the `WIKI_TOKEN` secret is a
fine-grained PAT, and fine-grained PATs cannot access wikis) turned out to be
only half the story. Two probes pointed the wrong way before a real push settled
it: cloning a **public** wiki needs no credentials at all, so a read-only token
passed the clone probe and only the push was denied; and `git push --dry-run` on
an **up-to-date** branch short-circuits with "Everything up-to-date" without
testing write access. Once the workflow attempted the real push, `GITHUB_TOKEN`
with `contents: write` **succeeded** - it does push to a public repo's wiki,
against the common claim that it cannot - and it is now preferred, with the
dead `WIKI_TOKEN` reduced to an override.
**Impact:** (a) the sync moved out of YAML into `scripts/sync-wiki.py`, where it
can be run and checked without pushing anything: `docs/README.md` becomes
`Home.md` (the previous job deleted Home and never recreated it, leaving the wiki
with no front page), links between docs become extension-less wiki links, and the
40 links that point into the repo (`infra/README.md`, `LICENSE`) become absolute
`blob/master` URLs instead of 404s. (b) `permissions: contents: write` is
declared, and the push is the credential probe, falling back and finally failing
with an actionable message. (c) The job no longer treats a synced wiki as an
error.
**Alternatives Considered:** minting a classic PAT with `repo` scope (the job's
own error text recommended it) was rejected as unnecessary once the built-in
token was measured to work - a broad, rot-prone credential in exchange for
nothing; translating the sed one-liners in place was rejected because that code
had no way to be exercised without pushing to the real wiki.
**Verification:** end-to-end rather than a green tick - a marker line was pushed
directly into the wiki's `Home.md`, the workflow dispatched, and a fresh clone
returned 71 pages with the marker gone and `Sync docs/ from <sha>` as the newest
commit. Locally the generator renders 71 pages with `Home.md` present, zero links
still ending `.md`, and zero non-page relative links. Live: `/wiki/user-guide`,
`/wiki/faq.ja`, `/wiki/install-windows.zh-Hans` and `/wiki/LANGUAGES` all 200
with real rendered headings.

`$0/para siemprerong>`. Both were invisible to assertions on `lang`, `hreflang`,
heading counts and byte-diffs, and both were obvious within seconds of rendering
the page.
**Impact:** (a) `localize_urls()` prefixes every relative URL with `../` on a
locale page, and `app.js` resolves its data files against the script's own URL so
it is correct at any page depth. (b) Overlapping units are resolved before
rendering: an enclosing unit whose text is identical to the unit inside it stands
down (the inner one renders the same words and keeps the markup), otherwise the
enclosing one wins because it carries the whole phrase. (c) Two guards now fail
the build on the artifact itself - `stray_text_gt()` for a tag fragment left in
text, `unrooted_urls()` for a relative URL that would resolve under `/<tag>/` -
and they were confirmed to fire on the old output before the fix.
**Alternatives Considered:** a `<base href="../">` element would have fixed the
HTML and the script's fetches in one line, but it changes resolution for every
relative URL and fragment on the page, and these pages already carry absolute
canonical and `hreflang` URLs; explicit prefixing keeps the generated markup
readable and independently checkable. Dropping the enclosing unit in every nested
pair was rejected because a paragraph whose inner text is only a fragment would
keep its English remainder (which is the mixed-language state the old output was
actually in).
**Verification:** rendered in a real engine (Bun.WebView) against a local static
server: `de`, `ru` and the mobile breakpoint all load with the stylesheet applied,

the mobile switcher reachable after opening the hamburger menu. Guards fire on
the previous output (10-26 strays per page) and pass on the new one; the extractor
and generator `--check` runs both exit 0.
**Left unfixed, deliberately:** a block containing an inline link or `<code>` is
skipped as a unit, so ~27 of 174 Spanish text blocks remain English while their
bold fragments are translated. A correct fix needs placeholder-based extraction
and a retranslation of all eight catalogs - a separate wave, not a patch.

### 2026-10-01: append-history.sh silently discarded every append past ~93 snapshots

**Agent:** DevOps + QAEngineer
**Status:** Accepted
**Rationale:** asked what I would fix as maintainer, I went back to the one thing I had left
unexplained. Reproduced cleanly: appends 1..93 recorded, then EVERY append from 94 to 400
a silent no-op that exited 0. A dropped append was indistinguishable from a successful one.

**Mechanism, confirmed in source:** `append-history.sh` passed the whole history as ONE
command-line argument (`--argjson prev "$prev"`). Past the argument limit - 32 KiB on
Windows, **128 KiB per-argument on Linux** (`MAX_ARG_STRLEN`) - jq fails, and the fallback
`[ -z "$result" ] && result="$prev"` keeps the previous document while still exiting 0.
A live scale check made this concrete: the real history is **1.7 MB at 84 snapshots**
(~20 KiB each), projecting to 7.4 MB at the 360 cap.

**Why it survived:** its own test could not catch it. The fixtures are ~250 bytes, so 400
appends total only ~100 KiB and stay just under Linux's 128 KiB limit - the suite was
green **on the edge of the cliff**. And the script is not on the production path
(`pages.yml` calls `collect-metrics.sh`), which had already fixed this exact thing and
says so in a comment: *"travel as files rather than --argjson: past ARG_MAX the jq run
produced [failure]"*.

**Fix (`04c3a59`):** ported the sibling's approach - payloads travel as files
(`--slurpfile`), bound inside the jq program so all 15 variable references are unchanged -
and a failed computation now **fails loudly with a diagnostic** instead of silently keeping
the old history. Verified: the 400-append loop went frozen-at-93 -> caps-at-360, and
`test_append_history.sh` went from 4 failures to all assertions passing.

**Guard (`6f6546e`):** a regression case with production-sized snapshots. Measured rather
than assumed - a first attempt (80 relays x 12) reached only 87,099 bytes, BELOW the
131,072 limit, and would have passed against the broken code. Sized up to 160 relays x 15
=> **216,032 bytes**, above the limit, so it fails against `--argjson`.

**Containment established by sweep, not assumption:** every other `--argjson` caller
passes a fleet-bounded payload (<= 10 nodes) or a scalar. The two scripts that handle the
big history in production - `collect-metrics.sh` and `health-anomaly.sh` - already use
`--slurpfile`. So the defect was real but contained to one non-production script.

**Withdrawn recommendation:** I had listed `.gitattributes` as a small win. It is not -
