### 2026-11-16: ALPN for the QUIC control plane is versioned, and the client ships first

**Agent:** net-eng (plan), lead (integration)
**Status:** Proposed — the wire-visible release and every relay flip need the owner
**Rationale:** an ALPN-less QUIC control plane is non-conforming (RFC 9001 §8.1) and any strict peer answers with alert 120, which is what #140/#147 report; the repo has never set ALPN on either side. The interop matrix (proven from the vendored rustls 0.23.46 / quinn 0.11 branches, not from memory) shows the asymmetry that decides the order: an ALPN-offering client that falls back to an empty list on `crypto(0x78)` recovers against an old relay (one extra handshake per process/relay), but an ALPN-requiring relay breaks every installed client with no recovery path. The client therefore must ship before any relay requires ALPN.
**Impact:** plan is `docs/quic-alpn-rollout.md`: identifier `lightspeed-control/1` in `protocol/src/control.rs`, client two-attempt connect with per-relay memory and a negotiated-protocol log field, relay `[network] control_alpn = "off" | "required"` (default off, no new port), startup/`/health`/`/metrics` observability, a canary gate of >=200 accepted handshakes with zero `rejected_no_application_protocol`, and per-relay rollback (`off` + restart). Stages 0-5; no calendar dates. Implementation tasks are tracked in the plan §13 and board tasks 4/5.
**Alternatives Considered:** flipping relays first (rejected: row B breaks the installed base permanently); a dual-port "optional ALPN" mode (rejected: registry schema change, a second TOFU pin key, per-relay firewall changes, client port probing); client-only fallback without ever setting ALPN (rejected: leaves the protocol non-conforming and the 120 cause unaddressed); do nothing (rejected as above).
**Verification:** the plan's matrix rows are pinned to vendored dependency branches recorded in `wat/evidence/2026-11-16/alpn/rustls-alpn-negotiation.txt`; 17 relative links check out; no code change in this round. Empirical confirmation is the plan's two-relay manual check, not yet run.

### 2026-11-16: A dead data plane must be visible in status, and a fallback verdict must name the failing side

**Agent:** lead (RustDev + QAEngineer contracts; single-threaded)
**Status:** Accepted (`client/src/engine.rs`, `client/src/interceptor/`, `client/src/capture/windivert_redirect.rs`, `client-gui/src/app.rs`)
**Rationale:** issue #167's report ended in `WinDivert recv failed 6 times consecutively: Invalid handle (os error 6)`, yet the app kept reporting an active interceptor and never showed an error for the rest of the session. Three state defects combined: `EngineStatus.interceptor_error` was reset at start and never written from `InterceptorStats.last_error`; `InterceptorHandle::is_active()` only asked whether the shutdown signal had been sent, which stays true after the receive thread dies; and `ERROR_INVALID_HANDLE` was classified as transient, so the loop spent its five-retry/310 ms budget before the only fatal message appeared. Separately, the no-reply watchdog counted every proxy datagram, including keepalive echoes and undecodable frames, as a "return", so a relay that only echoed our probes could be reported as a local injection fault, and two of its three verdicts omitted the error fields that answer "which side failed".
**Impact:** a fatal receive failure now reaches `EngineStatus.interceptor_error` (the tray's Error state already consumes it) and flips `interceptor_active` false; `ERROR_INVALID_HANDLE` ends the loop immediately in both WinDivert backends with a message that says interception stopped; a new `packets_reply_data` counter (decoded, non-keepalive) is what the GUI watchdog baselines, while `packets_from_proxy` keeps its all-datagrams display meaning; and all three watchdog messages carry `errors=` and `last_error=`. No wire change, no new UI surface.
**Alternatives Considered:** offering a "restart interception" button now (rejected: that is a UI feature and needs an interface-design pass; the missing *signal* is what this round fixes); changing `packets_from_proxy` itself to exclude keepalives (rejected: it would silently change a user-visible diagnostic number and the legacy redirect backend does not share that accounting); classifying error 6 inside each backend instead of the shared predicate (rejected: the predicate already owns "must the receive loop exit", and both backends would drift).
**Verification:** reverting the four fix sites in place makes 5/5 focused tests fail, restoring them makes them pass (`wat/evidence/2026-11-16/mutation-check.log`); the restore had to touch mtimes because cargo reused mutated binaries otherwise. Gate on the committed tree: fmt clean; workspace clippy `--all-targets --all-features` clean; 1,449 workspace tests (29 suites) / 155 GUI / 1,201 WinDivert-feature / 827 QUIC-feature passed, 0 failed (`wat/evidence/2026-11-16/gates-final.log`). The live invalid-handle path is not yet reproduced end to end.

### 2026-11-16: QUIC alert 120 is diagnosed in the client; the ALPN migration stays owner-gated

**Agent:** lead, applying the net-eng audit in `wat/evidence/2026-11-16/quic/net-eng.md`
**Status:** Accepted for the diagnostic (`client/src/quic/mod.rs`); Proposed for the wire change
**Rationale:** #140/#147's failure is a peer-sent `CONNECTION_CLOSE` carrying rustls's no_application_protocol alert (QUIC crypto error 120). A relay built from this repository never sets ALPN, so it cannot send that alert; the responder is therefore not our relay, and a QUIC-terminating middlebox on the reporter's path is the leading explanation. The raw quinn Display chain reads like a local TLS fault, which is why the thread kept blaming the relay. Meanwhile a control plane with no negotiated ALPN is non-conforming (RFC 9001 §8.1) and only works because both ends are rustls with empty lists.
**Impact:** a failed handshake that matches alert 120 now produces a verdict naming the responder address, stating that it cannot be a LightSpeed relay and suggesting a QUIC-intercepting VPN/AV/ISP; the client's `ALPN=[]` offer is logged once at debug so a capture can be compared to the log. Any other handshake error keeps its raw wording. The ALPN migration itself is deliberately not implemented: it is wire-breaking (old relays reject an ALPN-offering client with the same 120, and old clients reject an ALPN-only relay), so it needs the client-with-empty-ALPN-fallback released first, then relays enabled, then ALPN required, plus an owner decision.
**Alternatives Considered:** shipping ALPN on both sides now (rejected: it breaks every not-yet-updated relay/client pair in the fleet and needs a release plan); making the client retry with an empty ALPN after 120 without the verdict (rejected as the only step: it masks the diagnosis and still needs deployed relays to accept both policies); editing the issue thread with this finding (rejected here: public posting is an owner gate).
**Verification:** the classifier is pinned by `alert_120_is_explained_as_a_peer_that_cannot_be_our_relay` and `other_handshake_failures_keep_the_raw_error`; mutating the alert check to `if true` fails the first test with the raw rustls string (`wat/evidence/2026-11-16/quic-mutation.log`). `cargo test --workspace --lib --exclude lightspeed-gui --features quic`: 3 suites, 827 passed, 0 failed, 1 ignored.

### 2026-11-12: A relay-side TCP connection belongs to the client that created it

**Agent:** RustDev + SecOps
**Status:** Accepted (`proxy/src/relay.rs`, `proxy/tests/integration_security.rs`)
**Rationale:** the v5 5-tuple is supplied in the tunnel header and the connection table is relay-global. With no owner stored, any client with a valid token could present another client's tuple and RST, FIN, or splice its stream; two clients behind different NATs presenting the same tuple could also collide.
**Impact:** `TcpConnState` stores the creating client's address. A non-SYN packet from any other address is dropped and counted as an auth rejection, and a SYN that finds another client's tuple is refused. This applies to the unreleased both-transports path.
**Verification:** new unit test `a_tcp_connection_belongs_to_the_client_that_opened_it` and integration test `a_tcp_connection_is_owned_by_the_client_that_opened_it` (the owner's RST still tears the connection down; another client's does not).

### 2026-11-12: A known game server overrides the client-leg race

**Agent:** RustDev
**Status:** Accepted (`client-gui/src/app.rs`)
**Rationale:** the client-leg race answers "which relay is closest to me"; once the interceptor has locked the game server, the only question that matters is which relay is closest to that server. The ranking module already sorts by the destination leg first, but `poll_relay_race` could still apply its client-leg winner when a server was known but no choice had been recorded, and `poll_relay_measurement` could restart the data plane mid-match.
**Impact:** `should_apply_race` now takes `server_known` and declines the race; the destination-aware choice is applied only while tunnelling is withheld, otherwise it is staged for the next session. Before any server is known there is no server-relative latency, so the initial connection remains a provisional control-plane choice and the HOLD keeps game traffic off it.
**Verification:** GUI 136 passed; the route-ranking suite 10 passed; the test `a_pinned_relay_a_live_connection_or_a_known_server_beats_a_late_race_result` pins the new predicate.

### 2026-11-12: A race winner is identified by relay IP, at every comparison

**Agent:** RustDev + QAEngineer
**Status:** Accepted (`client-gui/src/app.rs`, regression tests in the same file)
**Rationale:** the client-leg race measures each relay's `/health` endpoint on port 8080, while the proxy list stores the advertised data port 4434. `poll_relay_race` compared whole addresses, so every winner failed the lookup and the function returned without logging anything: a clean first run never connected, and the next launch connected to the first registry entry. The same full-address comparison sat in `consider_connected_winner` and `poll_winner_probe`, which disabled continuous re-evaluation too.
**Impact:** `proxy_index_for` and `same_relay_endpoint` compare the relay IP at all three sites and warn when a winner is not in the list. A clean run now logs `Auto-selected the fastest relay <data-address>` and connects.
**Verification:** `cargo test -p lightspeed-gui` 136 passed; the two new tests pin a health-port winner resolving to its data-plane entry, and the connected relay being recognised across ports.
