### 2026-11-17: Registry metadata is stamped by the signer, not re-signed on a schedule

**Agent:** lead
**Status:** Accepted
**Rationale:** the network audit flagged that `web/registry.json`'s `published_at` (2026-09-20) predates the payload's `issued_at` (2026-09-22), and the round initially listed "re-sign with the owner's offline key" as an open action. Owner pushback ("doesn't github do that, is that breaking anything, we shouldn't need my local repo; github actions should handle anything recurring") triggered a re-read of the code: `published_at` is used by the client only as a **monotonic anti-rollback floor** (`reject_registry_rollback`, persisted last-seen value), `issued_at` was not modelled at all (serde dropped it), and there is no max-age/expiry check anywhere. So the stale value breaks nothing, and re-signing is only needed when the node set or revocations change - a rare, deliberately offline event, not recurring work for GitHub Actions. The real defect was tooling: the signer took the input timestamps verbatim and would silently drop `issued_at` on any re-sign because `Registry` did not model it.
**Impact:** `Registry` now models `issued_at` (optional, informational, preserved on re-sign and omitted when absent); `client/examples/sign_registry.rs` stamps `published_at = max(now, previous + 1)` and `issued_at = now` by default (with `--keep-timestamps` for an unchanged re-sign); two tests pin the round-trip and the omission; `docs/operator-key-succession.md` and the network audit's F2 entry record that no scheduled re-sign exists or is needed. No key material moves to GitHub; no workflow or credential is added; the static file stays served by GitHub Pages.
**Alternatives Considered:** re-sign now with the owner key (rejected: changes the live signed document for zero functional gain); add a scheduled GitHub Actions job that re-signs with the operator key (rejected: stores the offline signing key in Actions for a task that has no cadence); add a client-side max-age (rejected: a real behaviour change, and a revoked node staying trusted on an offline client is a separate decision in `docs/operator-key-succession.md` §4).
**Verification:** client registry suite (round-trip, omission, existing verify/rollback tests) green; `cargo fmt`/`clippy` clean; published registry still verifies against the compiled key (test `test_web_registry_verifies_against_operator_key`); audit F2 corrected in place.

### 2026-11-16: ALPN for the QUIC control plane is versioned, and the client ships first

**Agent:** net-eng (plan), lead (integration)
**Status:** Proposed — the wire-visible release and every relay flip need the owner
**Rationale:** an ALPN-less QUIC control plane is non-conforming (RFC 9001 §8.1) and any strict peer answers with alert 120, which is what #140/#147 report; the repo has never set ALPN on either side. ### 2026-11-16: A dead data plane must be visible in status, and a fallback verdict must name the failing side

**Agent:** lead (RustDev + QAEngineer contracts; single-threaded)
**Status:** Accepted (`client/src/engine.rs`, `client/src/interceptor/`, `client/src/capture/windivert_redirect.rs`, `client-gui/src/app.rs`)
**Rationale:** issue #167's report ended in `WinDivert recv failed 6 times consecutively: Invalid handle (os error 6)`, yet the app kept reporting an active interceptor and never showed an error for the rest of the session. ### 2026-11-12: A relay-side TCP connection belongs to the client that created it

**Agent:** RustDev + SecOps
**Status:** Accepted (`proxy/src/relay.rs`, `proxy/tests/integration_security.rs`)
**Rationale:** the v5 5-tuple is supplied in the tunnel header and the connection table is relay-global.
