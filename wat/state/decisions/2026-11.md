### 2026-11-16: DeepSeek Harness is the only agent harness; procedures are project skills

**Agent:** lead, with Architect review of the instruction chain
**Status:** Accepted (`AGENTS.md`, `.dsh/skills/`, `wat/rules.md`, `wat/archive/README.md`)
**Rationale:** the repository had been driven by an opencode-based agent and then by a harness that kept state in `.omo/`, but neither left a working configuration behind; `AGENTS.md` still claimed to be tool-neutral and gave no DSH tool mapping, no Team mode, and no Windows rules. The decisive fact was discovered in this migration: on Windows, `wat/archive/agents.md` is case-insensitively `AGENTS.md`, so DSH's workspace-instruction loader injected the persona document into every session as project rules. A single documented instruction chain removes that class of bug.
**Impact:** `AGENTS.md` is the only instruction file (119 lines) and points at four project skills in `.dsh/skills/` (`lightspeed-wat`, `lightspeed-team`, `lightspeed-windows`, `lightspeed-verify`). `[AGENT_STUB]` in `wat/rules.md` records the rule; `docs/agent-operations.md` documents it for humans; the old persona file is deleted and its content lives in `wat/personas/`.
**Alternatives Considered:** keeping the personas in `archive/` and renaming only the file to `personas.md` (rejected: still a one-word collision away from `AGENTS.md`); duplicating the procedures into `AGENTS.md` (rejected: every session pays for all four procedures, and they drift); installing a DSH plugin/bundle to hold the procedures (rejected: the repo should work in any DSH profile without an install step).
**Verification:** skill discovery observed live (the session catalog updated as each `SKILL.md` appeared, and all four are invocable by name); `Test-Path wat/archive/AGENTS.md` returned true before the deletion and false after, with DSH emitting `Instructions removed: wat\archive\AGENTS.md`.

### 2026-11-16: Personas are delegation contracts, and Team mode is the coordination mechanism

**Agent:** lead (Architect + QAEngineer review)
**Status:** Accepted (`wat/personas/`, `wat/team-mode.md`, `AGENTS.md`)
**Rationale:** DSH Agent Teams gives a shared task board to ordinary subagents; it does not carry role definitions. The old `agents.md` prose had no slugs, ownership boundaries or acceptance criteria, so it could not be used to create or assign work. A persona that cannot be pasted into a delegation prompt is documentation, not an operating element.
**Impact:** eight personas (`architect`, `rust-dev`, `infra-dev`, `net-eng`, `qa-engineer`, `sec-ops`, `dev-ops`, `interface-designer`), one file each, with mission, ownership, must/must-not, definition of done, paste-ready delegation brief and a `team_task_create` template. The roster is machine-readable (`wat/personas/personas.json` + schema). `wat/team-mode.md` specifies enabling the mode, task conventions (`[<slug>] ...`), compare-and-set revisions, ownership/reassignment rules, the envelope, failure modes and the degraded mode when Team is off.
**Alternatives Considered:** one combined personas file (rejected: a delegation only needs one persona, and a combined file is read in full); per-persona DSH plugins (rejected: plugins are profile state, not repository state, and would not follow the checkout); encoding personas only in `AGENTS.md` (rejected: it grows the always-loaded prompt and blurs role boundaries).
**Verification:** `personas.json` and its schema parse; 8/8 files exist; slugs match the subagent-name grammar; skill `lightspeed-team` loads and the session catalog lists it. Team-mode tool semantics were taken from the installed `dsh-agent-team`/`dsh-tool-agent-team` READMEs for `0.2.2-rc.3`, not from memory.

### 2026-11-16: State is a small hot file plus append-only month archives

**Agent:** lead (Architect)
**Status:** Accepted (`wat/state/`, `tools/Migrate-PhaseLog.ps1`)
**Rationale:** `current-phase.md` was read at the start of every session and had grown to 322,758 bytes / 5,727 lines, one third of it a duplicated copy of the October phase blocks (29 duplicate phase blocks, 15 duplicate dated entries). The duplication was not harmless: the copies had drifted (`**Last updated:** 2026-10-18` appeared only in the truncated tail), so two readers could take different facts from the same file. `decisions.md` had the same shape problem in a smaller size: 138,359 bytes with the template embedded mid-log and September entries out of order.
**Impact:** `current-phase.md` is now under 8 KB / about 125 lines including this round's entry (4,579 bytes / 71 lines immediately after the split); history lives in `wat/state/phases/2026-09.md` and `2026-10.md` with an index. Decisions are a 47-line index plus seven monthly files (74 entries preserved, sorted, headings normalised). Rotation is manual by design; `tools/Migrate-PhaseLog.ps1` reproduces the one-off migration and refuses to run on a migrated log.
**Alternatives Considered:** keeping one file and relying on `read` offsets (rejected: the file is loaded by agents, not paginated by the harness, and the duplicates would remain); deleting pre-October history (rejected: history is the audit trail for releases and rollbacks); auto-rotating by date (rejected: recency is not the same as relevance).
**Verification:** line-level preservation check (4,613 non-empty original lines; only the replaced H1 and one stale line from the truncated duplicate are absent); 74/74 decision entries present with unique date+title; zero duplicate headings in the month files.

### 2026-11-12: A relay-side TCP connection belongs to the client that created it

**Agent:** RustDev + SecOps
**Status:** Accepted (`proxy/src/relay.rs`, `proxy/tests/integration_security.rs`)
**Rationale:** the v5 5-tuple is supplied in the tunnel header and the connection table is relay-global. With no owner stored, any client with a valid token could present another client's tuple and RST, FIN, or splice its stream; two clients behind different NATs presenting the same tuple could also collide.
**Impact:** `TcpConnState` stores the creating client's address. A non-SYN packet from any other address is dropped and counted as an auth rejection, and a SYN that finds another client's tuple is refused. This applies to the unreleased both-transports path.
**Verification:** new unit test `a_tcp_connection_belongs_to_the_client_that_opened_it` and integration test `a_tcp_connection_is_owned_by_the_client_that_opened_it` (the owner's RST still tears the connection down; another client's does not).

### 2026-11-12: A known game server overrides the client-leg race

**Agent:** RustDev
**Status:** Accepted (`client-gui/src/app.rs`)
**Rationale:** the client-leg race answers "which relay is closest to me"; once the interceptor has locked the game server, the only question that matters is which relay is closest to that server. The ranking module already sorts by the destination leg first, but `poll_relay_race` could still apply its client-leg winner when a server was known but no choice had been recorded, and `poll_relay_measurement` could restart the data plane mid-match.
**Impact:** `should_apply_race` now takes `server_known` and declines the race; the destination-aware choice is applied only while tunnelling is withheld, otherwise it is staged for the next session. Before any server is known there is no server-relative latency, so the initial connection remains a provisional control-plane choice and the HOLD keeps game traffic off it.
**Verification:** GUI 136 passed; the route-ranking suite 10 passed; the test `a_pinned_relay_a_live_connection_or_a_known_server_beats_a_late_race_result` pins the new predicate.

### 2026-11-12: A race winner is identified by relay IP, at every comparison

**Agent:** RustDev + QAEngineer
**Status:** Accepted (`client-gui/src/app.rs`, regression tests in the same file)
**Rationale:** the client-leg race measures each relay's `/health` endpoint on port 8080, while the proxy list stores the advertised data port 4434. `poll_relay_race` compared whole addresses, so every winner failed the lookup and the function returned without logging anything: a clean first run never connected, and the next launch connected to the first registry entry. The same full-address comparison sat in `consider_connected_winner` and `poll_winner_probe`, which disabled continuous re-evaluation too.
**Impact:** `proxy_index_for` and `same_relay_endpoint` compare the relay IP at all three sites and warn when a winner is not in the list. A clean run now logs `Auto-selected the fastest relay <data-address>` and connects.
**Verification:** `cargo test -p lightspeed-gui` 136 passed; the two new tests pin a health-port winner resolving to its data-plane entry, and the connected relay being recognised across ports.
