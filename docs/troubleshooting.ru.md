## Быстрая диагностика

Сначала запустите встроенную проверку среды — она выявляет большинство проблем:

```bash
lightspeed --check
```

При этом проверяются: доступность перехватчика, инструменты фильтрации пакетов, разрешение игрового профиля и подключение прокси.

---

## Распространенные проблемы

### «Перехватчик недоступен»

**CLI:** В вашей ОС нет необходимых инструментов фильтрации пакетов или вам не хватает привилегий.

| ОС | Требуется | Как исправить |
|----|----------|------------|
| Линукс | nftables или iptables + root | `sudo lightspeed ...` |
| macOS | pfctl (встроенный) + root | `sudo lightspeed ...` |
| Окна | Драйвер WinDivert + Администратор | Щелкните правой кнопкой мыши → Запуск от имени администратора |

Подтвердите с помощью:
```bash
lightspeed --check
```

### «Игровой трафик не виден» / Отправленные пакеты остаются на уровне 0

**CLI:** Перехватчик не может найти игровые пакеты в ожидаемом диапазоне портов.

1. Убедитесь, что ваша игра **подключена к серверу** (а не только к главному меню или лобби).
2. Проверьте игру с помощью `--scan-processes`:
   ```bash
   lightspeed --scan-processes
   ```
3. Попробуйте другой игровой профиль или используйте ручной режим сервера.

**Графический интерфейс (Windows):** Подождите 15 секунд. Если появляется желтый баннер «⚠ Игровой трафик не виден»:
1. Откройте PowerShell с повышенными правами:
   ```powershell
   Get-NetUDPEndpoint -OwningProcess (Get-Process RustClient).Id |
     Where-Object LocalPort -gt 1024 |
     Select-Object LocalPort
   ```
2. Используйте порт, указанный в разделе **Дополнительно → установите сервер вручную**.

### «🎯 Нахождение игрового сервера…» никогда не решается

Детектор не увидел 3 пакета в одно и то же место назначения в течение 1,5 секунд.

1. Убедитесь, что вы подключены к игровому серверу (перемещайте персонажа для генерации трафика)
2. Если пакеты по-прежнему не обнаруживаются через 15 секунд, ваш сервер использует нестандартный порт — используйте ручной режим сервера.
3. Остановите и перезапустите перехватчик после подключения к серверу.

### Пакеты отправлены вверх, доставлено пакетов = 0

Пакеты доходят до прокси, но ответы не доходят до вашей игры. Обычно проблема с брандмауэром.

**Линукс:**
```bash
sudo iptables -I INPUT -p udp --sport 4434 -j ACCEPT
```

**macOS:**
```bash
sudo pfctl -d  # Temporarily disable pf to test
```

**Окна:**
```powershell
# Check if the stable rule exists (one rule, not one per boost)
netsh advfirewall firewall show rule name="LightSpeed WinDivert Tunnel"

# Add it manually if missing
netsh advfirewall firewall add rule name="LightSpeed WinDivert Tunnel" protocol=UDP dir=in action=allow program="C:\path\to\lightspeed-gui.exe"
```

Правила из старых сборок назывались `LightSpeed WinDivert Tunnel <port>`; текущий
сборки удаляют тот порт, который они используют, и сохраняют одно стабильное правило. Любой
оставшиеся правила для каждого порта можно безопасно удалить:
`netsh advfirewall firewall delete rule name="LightSpeed WinDivert Tunnel 4434"`
(соответствует порту, указанному `netsh advfirewall firewall show rule name=all`).

### `sendmsg error: ... 10040` / `WSAEMSGSIZE` (Windows) или `EMSGSIZE` (Linux/macOS)

Дейтаграмма, которую пытался отправить клиент, превышает **реальный** MTU пути.
ограничение туннеля по умолчанию составляет 1492 байта (безопасно для PPPoE), но VPN, прокладка DPI, такая как
Zapret или адаптер с уменьшенным MTU может быть меньше, поэтому пакет подходит для зажима.
по-прежнему отвергается ОС (`Windows error 10040`).

Исправлено — уменьшите ограничение path-MTU туннеля в `config.toml`:

```toml
[tunnel]
# 1280-1500. Start at 1400, then 1350 if the error persists.
mtu = 1400
```

или передайте `--mtu 1400` в CLI. Текущие сборки также снижают бюджет.
автоматически, когда отправка отклонена, повторите эту дейтаграмму один раз с помощью
разрешена фрагментация, а в статусе записана ошибка ОС вместо
сообщая о том, что реле молчало.

Немедленное решение, пока клиент не изменился: понизьте адаптер Windows.
MTU, чтобы игра отправляла пакеты меньшего размера, затем перезапустите игру:

```powershell
netsh interface ipv4 show subinterfaces
netsh interface ipv4 set subinterface "Ethernet" mtu=1400 store=persistent
```

### Проверка работоспособности прокси не удалась

```bash
# Test connectivity
curl http://YOUR_PROXY_IP:8080/health

# Expected response:
# {"status":"ok","node_id":"relay-1","uptime_secs":86400,...}
```

Если недоступен:
- Проверьте, работает ли прокси: `systemctl status lightspeed-proxy`.
- Проверьте, что брандмауэр разрешает UDP 4434 и TCP 8080.
- Проверьте логи прокси: `journalctl -u lightspeed-proxy --tail 50`.

### Плоскость управления QUIC не работает с `error 120`/`no_application_protocol`

Клиенту не удалось завершить подтверждение связи плоскости управления QUIC с помощью реле. Когда
повторная попытка одноразового пустого предложения также не удалась, журнал заканчивается этим вердиктом (цитируется
дословно от клиента; `{err}` — это основная ошибка QUIC, а `{addr}` —
адрес ответчика):

```text
{err}: the responder at {addr} closed the QUIC handshake with TLS alert 120 (no_application_protocol), and the empty-offer retry also failed. The client cannot tell these two causes apart from the handshake alone: (1) a QUIC-intercepting middlebox on this path (VPN/AV/ISP) that does not carry the ALPN extension (see #140); or (2) a LightSpeed relay on a different ALPN revision -- version skew, where the relay requires an ALPN name this client does not offer.
```

**То, что клиент уже сделал.** Текущие клиенты всегда предлагают версию имени ALPN.
`lightspeed-control/1`. Если реле отвечает предупреждением TLS 120, клиент повторяет попытку.
**один раз** с пустым предложением ALPN, а затем запоминает ответ этого ретранслятора до конца
процесса, поэтому при нормальной работе клиента обреченное дополнительное рукопожатие происходит в
чаще всего один раз на реле за запуск. Успешный откат является нормальным для реле, которое
не было обновлено (по умолчанию реле `[network] control_alpn = "off"`):
В строке `QUIC connection established` отображается `alpn=none`, и регистрация продолжается.

**Что означает окончательная неудача.** Повторная попытка с пустым предложением также не удалась, поэтому есть
ровно две возможности, и одно лишь рукопожатие не может отличить их друг от друга:

1. **Промежуточный блок, перехватывающий QUIC**: VPN, антивирус/брандмауэр с
   Проверка HTTPS/QUIC или оборудование интернет-провайдера, не имеющее расширения ALPN.
   ([#140](https://github.com/ShibbityShwab/lightspeed/issues/140)). Если каждое реле
   в одной сети выходит из строя, а в другой те же реле работают, путь общий
   фактор.
2. **Несовпадение версий** — реле требует версии ALPN, которую этот клиент не предлагает.
   (например, реле установлено на `control_alpn = "required"` и работает по протоколу
   версия новее, чем этот клиент). По замыслу это проваливается громко, а не молчаливо.
   понижение версии: текущий клиент против реле на `lightspeed-control/1` согласовывает,
   и ретранслятор, требующий чего-либо, чего не предлагает этот клиент, отклоняет это со значением 120.

**Как сузить круг:**

- Запустите `lightspeed-client --test-control --proxy <relay-ip>`, чтобы увидеть, на каком этапе это происходит.
  реле находится в положении. Значение `alpn=` на подключенной линии и в итоговой сводке — это
  согласованный протокол приложения: `lightspeed-control/1` означает, что реле приняло
  предложение с версией, `none` означает, что оно приняло пустое предложение после резервного варианта (более старая версия предложения).
  реле), и запуск, завершившийся неудачей по вердикту этого раздела, описан выше.
- Если в этой сети выходит из строя каждое реле, но те же реле работают в других местах, заподозрите
  Промежуточный блок: отключите VPN или проверку HTTPS/QUIC продукта безопасности и повторите попытку,
  затем прикрепите захват UDP 4433 к #140.
- Если выходит из строя только одно реле, сравните режим ALPN этого реле со сборкой вашего клиента:
  строка запуска реле и поле `control_alpn` на его `GET /health` сообщают о
  настроенный режим (см. [Справочник по CLI](CLI-REFERENCE.md#proxy-configuration)). Если ты
  управлять этим реле, `control_alpn = "off"` восстанавливает предыдущее поведение для старых
  клиенты; процедура оператора и правило заказа «сначала клиент» находятся в
  [Развертывание прокси](deploy-proxy.md) и [план развертывания ALPN](quic-alpn-rollout.md).

### Игра отключается при запуске перехватчика

Перехватчик перехватывает пакеты до того, как игра сможет получить ответы, и путь внедрения завершается сбоем.

**Окна:**
1. Убедитесь, что `WinDivert64.sys` и `WinDivert.dll` находятся рядом с `.exe`.
2. Отключите дополнительные сетевые адаптеры (виртуальные адаптеры Docker, VMware, Hamachi).
3. Подключитесь к игровому серверу **перед** запуском перехватчика.

**Линукс:**
1. Проверьте правила nftables: `sudo nft list ruleset | grep lightspeed`
2. Если правила устарели: `sudo lightspeed --check` для диагностики.

### «Ошибка открытия WinDivert» / `FWP_E_IN_USE` (0x8032000A) в Windows

Только дескрипторы с настоящим фильтром перехвата — intercept (`udp and outbound …`) и shadow (`udp and inbound …`) — владеют WFP callout/фильтром. Закреплённый (pin) дескриптор, живущий весь процесс, и inject-дескриптор используют фильтр `"false"`, не перенаправляют трафик и не владеют объектом WFP. Поэтому WFP callout/фильтр — это не «один на каждый открытый дескриптор», а удерживаемый pin не является блокировкой состояния WFP: в полевом журнале от 23.11.2026 pin открыт, и следующее открытие intercept по-прежнему завершается ошибкой `FWP_E_IN_USE`.

`FWP_E_IN_USE` означает, что объект WFP всё ещё на кого-то ссылается (например, фильтр предыдущего процесса, который ядро не успело удалить после жёсткого завершения), либо что callout одновременно регистрируется/снимается с регистрации. «Ни один процесс не использует WinDivert на виду» не доказывает, что ссылки нет, а состояние WFP сейчас не снимается, поэтому не считайте текст ошибки первопричиной.

LightSpeed закрывает intercept-, inject- и shadow-дескрипторы на каждом штатном пути остановки (Ctrl+C в `--watch`/`--start-interceptor`, **Выход** в GUI), разблокирует цикл приёма через `WinDivertShutdown` перед закрытием и ждёт подтверждения от потоков-владельцев. Эта детерминированность относится к **владению дескрипторами** приложением; WFP teardown в ядре — отдельный путь, и его ошибки не видны из пользовательского пространства.

Если это всё ещё происходит:

1. **Повторите Start один раз.** Следующий патч автоматически повторяет `FWP_E_IN_USE` при удерживаемом pin (с ограничением ~5 с) и может один раз пересоздать pin; 1.12.5 повторяет только когда pin **не** удерживается, поэтому там повтор означает Stop и снова Optimize.
2. **Завершите работу штатно и подождите немного**: используйте Ctrl+C в CLI или **Выход** в GUI, затем дайте дескрипторам одну-две секунды на закрытие перед повторным запуском.
3. **Остановите службу WinDivert** (требуются права администратора; это явный сброс, который LightSpeed не выполняет автоматически, и он затрагивает любое другое приложение на WinDivert на машине — сначала убедитесь, что другой клиент WinDivert не запущен):
   ```powershell
   sc stop windivert
   ```
4. **Полное выключение** — крайняя мера, и только если внешнего пользователя WinDivert исключить нельзя: **Перезагрузка** Windows может переиспользовать сеанс ядра с устаревшим состоянием, поэтому полное **Выключение → включение** — единственная надёжная очистка на уровне машины. Это не первое средство, и LightSpeed не будет советовать перезагрузку без этой причины.

WinDivert 2.2 держит драйвер загруженным после закрытия последнего дескриптора: провайдер WFP и его 20 подслоёв остаются (1 / 20), а `WinDivert64.sys` остаётся заблокированным до остановки службы или перезагрузки машины. Pin этого не меняет, и это не гарантия того, что драйвер выгрузится при Stop.

> **Совет:** в v1.2.2 и более ранних отдельная ошибка (аутентификация плоскости данных отвергала все пакеты, issue #59) замораживала соединение и заставляла пользователей многократно завершать клиент, что и вызвало большинство сообщений о `FWP_E_IN_USE`. Эта ошибка аутентификации исправлена в v1.2.3.

## Проблемы с графическим интерфейсом Windows

Они относятся к приложению `lightspeed-gui` в Windows.

### Выход ничего не сделал и оставил процесс-зомби

В версиях до версии 1.4.2 выбор **Выход** в меню панели задач мог оставить процесс работающим в фоновом режиме (зомби), поэтому окно закрывалось, но движок продолжал работать, а последующий запуск велся странно. Версия 1.4.2 исправляет это: Quit теперь корректно завершает процесс.

Если вы используете более старую сборку и процесс завис, завершите его вручную:

```powershell
Get-Process lightspeed-gui -ErrorAction SilentlyContinue | Stop-Process
```

Затем обновитесь до версии 1.4.2 или новее.

### Вместо фокусировки первого открывается второй экземпляр

В версиях до версии 1.4.2 при двойном запуске графического интерфейса складывалось второе окно и второй движок. Графический интерфейс теперь имеет защиту одного экземпляра: при втором запуске отображается краткое уведомление «LightSpeed ​​уже запущен» и происходит выход вместо запуска другого движка. Чтобы в любом случае принудительно создать второй экземпляр (для диагностики), передайте `--force` или установите `LIGHTSPEED_GUI_FORCE=1`.

### Реле не обнаружено

Графический интерфейс обнаруживает ретрансляторы сообщества через подписанный реестр. Если список реле остается пустым:

1. Убедитесь, что у вас есть доступ к Интернету и что брандмауэр или VPN не блокируют исходящий HTTPS-доступ к реестру.
2. Проверьте журнал графического интерфейса пользователя (см. ниже) на наличие ошибок выборки реестра или проверки подписи.
3. В сборке CLI запустите `lightspeed-client --probe-proxies`, чтобы напрямую просмотреть отчет об обнаружении и проверке. Если CLI также ничего не находит, проблема связана с сетью, а не с графическим интерфейсом.
4. Перезапустите графический интерфейс после устранения проблемы с подключением; обнаружение запускается при запуске.

### Как найти и открыть журнал графического интерфейса

Графический интерфейс записывает журнал трассировки в:

```
%LOCALAPPDATA%\Lightspeed\gui-trace.log
```

Вставьте этот путь в адресную строку проводника, чтобы открыть папку, затем откройте `gui-trace.log` в любом текстовом редакторе. Прикрепите его к отчету об ошибке.

### «Heartbeat 0 in» в журнале

Строка вида `Heartbeat 0 in` означает, что в текущем окне движок не отправил никаких сигналов подтверждения активности. На практике это проявляется, когда клиент еще не установил рабочее соединение с плоскостью управления, поэтому контрольные сигналы не исчезли. Распространенные причины:

- Клиент еще не зарегистрировался на реле (проверьте строку регистрации в просмотре статуса).
- Выбранное реле недоступно.
- Перехватчик не запущен, поэтому ни один сеанс не активен.

Как только регистрация успешна и сердцебиение начинает течь, счетчик увеличивается. Если он остается на уровне 0, пока реле показывает работоспособность, запустите `lightspeed-client --test-control`, чтобы определить, доступна ли плоскость управления.

## Журналы для отчетов об ошибках

Запустите журнал отладки для получения подробной диагностики:

```bash
# CLI
RUST_LOG=debug lightspeed --start-interceptor --game rust --proxy YOUR_PROXY:4434 2>&1 | tee lightspeed.log

# Windows GUI
cd C:\path\to\lightspeed
lightspeed-gui.exe 2>&1 | tee lightspeed-log.txt
```

Прикрепите файл журнала к своей [проблеме GitHub](https://github.com/ShibbityShwab/lightspeed/issues).
